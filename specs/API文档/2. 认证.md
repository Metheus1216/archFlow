# 2. 用户认证

> 目标接口尚未实现。当前登录表单的开发入口只写页面提示 Cookie；不能作为密码验证、GitHub 登录或访问控制的证据。共享定义位于 `auth.schema.ts`，公共凭证规则见[全局规范](./1.%20全局.md)。

## 2.1 注册

```http
POST /api/v1/auth/register
Idempotency-Key: <本次操作标识>
```

请求使用 `RegisterInput`：

```json
{ "username": "林杉", "email": "a@example.com", "password": "example123" }
```

邮箱通过 `Email` 统一去空白并转小写，用归一化值检查唯一性和存储；密码先哈希，不保存或返回明文。字段长度和格式见 Zod，不在此重复。

返回 `201`，数据使用 `AuthResult`，包含访问凭证、有效期和用户信息：

```json
{
  "accessToken": "eyJ...",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {
    "id": "usr_1",
    "username": "林杉",
    "email": "a@example.com",
    "avatarUrl": null,
    "createdAt": "2026-11-13T16:00:00+08:00"
  }
}
```

刷新凭证只通过 `Set-Cookie` 下发，不进入响应体。邮箱占用返回 `409 EMAIL_TAKEN`，普通字段非法按目标规范返回 `422 VALIDATION_FAILED`。

## 2.2 登录

```http
POST /api/v1/auth/login
```

请求使用 `LoginInput`，含邮箱和密码；返回 `200` 与 `AuthResult`，并设置刷新 Cookie。邮箱同样归一化，登录时不再要求已有密码满足未来可能变化的注册强度规则。

邮箱不存在和密码错误统一为 `401 INVALID_CREDENTIALS`，不区分原因。界面展示这一错误，不尝试刷新登录请求。

## 2.3 刷新访问凭证

```http
POST /api/v1/auth/refresh
```

无请求体，从 Cookie 获取刷新凭证。成功返回 `200` 与 `AccessTokenResult`，并替换刷新 Cookie。旧值立即失效；检测到复用时按设备会话族吊销并返回 `401 REFRESH_INVALID`。

前端多个请求同时过期时共用一个刷新请求。页面重新加载后也需要先刷新，才能恢复内存中的访问凭证。具体 Cookie 属性与开发环境策略见全局规范，不能把刷新凭证写入 localStorage。

## 2.4 退出登录

```http
POST /api/v1/auth/logout
Authorization: Bearer <accessToken>
```

请求可省略，传入时使用 `LogoutInput`：

```json
{ "allDevices": false }
```

默认吊销当前设备会话的刷新凭证；`allDevices: true` 吊销该用户全部刷新会话。服务端清除 Cookie，返回无响应体的 `204` 与 `X-Trace-Id`。前端同时清理访问凭证、提示 Cookie、用户缓存和活动连接。

## 2.5 查询当前用户

```http
GET /api/v1/auth/me
Authorization: Bearer <accessToken>
```

返回 `200`，`data` 直接是 `User`，不额外包 `{ user }`。此接口属于认证请求，不能因为位于 `/auth` 下而免鉴权。

## 2.6 申请重置密码（暂缓）

```http
POST /api/v1/auth/password/forgot
```

仅保留 `ForgotPasswordInput` 与目标行为，第一版不实现、不在前端接入。后续设计为统一返回 `202`、`data: null`，避免向调用者透露邮箱是否注册；仍需单独设计发送、频率限制和凭证存储。

## 2.7 执行重置密码（暂缓）

```http
POST /api/v1/auth/password/reset
```

仅保留 `ResetPasswordInput`，第一版不实现。后续成功返回 204 并吊销全部刷新会话；无效凭证使用 `RESET_TOKEN_INVALID`。流程立项后再补实际接口与测试。
