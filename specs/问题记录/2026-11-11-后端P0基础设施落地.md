# 后端 P0 基础设施落地（2026-11-11）

## 目标

把项目从“只有前端 mock”补到能承载真实 API 的地基：

1. 补齐 auth / agent / SSE / 文件 / 资产 / 系统接口的共享契约；
2. 把表设计里的 9 张表落成 TypeORM 实体与初始迁移；
3. 给 API 接上 PostgreSQL、Redis、MinIO；
4. 实现并全局注册 Zod 校验管道与统一异常过滤器。

P0 不包含业务 Controller，Auth / Project / Conversation 等模块从 P1 开始。

## 结论

- `packages/shared` 新增 6 个 schema 文件，现有契约覆盖 auth、project、knowledge、asset、conversation、agent、sse、system。
- `packages/db` 新增 9 个实体、初始迁移、DataSource 工厂和 `pnpm db:migrate` 脚本。
- `apps/api` 接入环境变量校验、数据库连接、Redis、MinIO，以及全局 Zod 管道/异常过滤器。
- 已在本地 PostgreSQL 实际执行迁移，验证了 9 张表、`vector(1536)`、HNSW/GIN/降序索引和 migration 记录。
- API 实际启动验证：PostgreSQL 已连接、MinIO bucket 就绪、404 返回统一外壳并带 `X-Trace-Id`。
- 当前 `/api/v1` 还没有业务路由；访问任意接口仍走 404 外壳，这是预期状态。

## 3. API 基础设施

### 3.1 环境变量

`apps/api/src/config/env.ts`：

- 用 Zod 校验 `NODE_ENV`、`PORT`、`WEB_ORIGIN`、`DATABASE_URL`、`REDIS_URL`、MinIO 配置；
- 启动时自动加载 `apps/api/.env`，其次读仓库根 `.env`；
- 依赖 `process.loadEnvFile`，因此根 `engines.node` 提升到 `>=20.12.0`。

### 3.2 数据库

`apps/api/src/database/database.service.ts`：

- 持有全进程唯一的 `DataSource`；
- `onModuleInit` 连接，`onApplicationShutdown` 销毁；
- 没有引入 `@nestjs/typeorm`。P0 只需要一个受生命周期管理的连接，后续模块直接注入 `DatabaseService`，少一层动态模块和额外依赖；如果以后需要多数据源或 `forFeature` 自动注入，再切换。

### 3.3 Redis / MinIO

`apps/api/src/infra/`：

- `RedisService`：ioredis 客户端；连接失败只记录日志，不阻塞 HTTP 启动；
- `StorageService`：MinIO 客户端；bucket 检查在后台执行，MinIO 不可用时只告警，不阻塞启动；
- `InfraModule` 为全局模块。

### 3.4 全局 Zod 管道

`apps/api/src/common/zod-validation.pipe.ts`：

- 支持两种用法：
  - DTO 类声明 `static readonly zodSchema = XxxInput`，全局管道自动读取；
  - Controller 里 `@Body(new ZodValidationPipe(XxxInput))`。
- 找不到 schema 时放行，不影响路径参数、文件流等非 DTO 入参。
- `ZodValidationException` 携带原始 issues；图相关错误通过 `{ graph: true }` 或 issue 的 `params.errorCode` 识别，映射 413 `GRAPH_TOO_LARGE` / 422 `GRAPH_INVALID`，其余为 400 `VALIDATION_FAILED`。
- `toFieldErrors` 把 issue 路径格式化成 `cards[0].values` 形式。

### 3.5 统一异常出口

`apps/api/src/common/http-exception.filter.ts`：

- 所有错误返回 `{ code, message, data: null, errors?, traceId }`；
- `ZodValidationException` → 400 / 413 / 422，附字段级 errors；
- `HttpException` → 保留模块设置的 `code`，否则按状态码兜底；
- 未知异常 → 500 `INTERNAL_ERROR`，记录堆栈但不对客户端泄漏；
- 从 `X-Request-Id` 读取合法 traceId，否则生成 UUID；响应写回 `X-Trace-Id`。

### 3.6 注册方式

`apps/api/src/app.module.ts` 通过 `APP_PIPE` / `APP_FILTER` 全局注册，所有 Controller 自动生效。`main.ts` 负责全局前缀、CORS、shutdown hooks，并在启动失败时输出可读日志后退出。

## 4. 本地环境

### 4.1 Docker

本机最初报：

```text
open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified
```

原因是 Docker Desktop 的 Linux engine 没有启动。启动 Docker Desktop 后 `docker info` 正常。

### 4.2 MinIO 镜像

`docker compose up -d` 时发现官方 `minio/minio:latest` 已无法从 Docker Hub 拉取（`pull access denied / repository does not exist`），Quay 也返回 401。

`docker-compose.yml` 改为：

```yaml
image: bitnamilegacy/minio:latest
user: "0:0"
```

`user: "0:0"` 是因为命名卷默认 root 所有，Bitnami 镜像默认用户 1001 写不了 `/data`。

**这是本地开发替代方案，不是生产选型。** P7 做文件上传前需要重新确认生产对象存储：官方 MinIO 镜像、外部 S3 或自建 MinIO。

### 4.3 容器

当前 compose 启动：

```text
archflow-postgres   pgvector/pgvector:pg16   Up (healthy)
archflow-redis      redis:7-alpine           Up (healthy)
archflow-minio      bitnamilegacy/minio      Up
```

端口：PostgreSQL `5432`、Redis `6379`、MinIO `9000/9001`。

## 6. 已知限制

- `/api/v1` 还没有业务 Controller，健康检查接口也尚未实现；当前所有路径都是 404 外壳。
- 404 兜底码是 `BAD_REQUEST`，因为 `ERROR_CODES` 没有通用 `NOT_FOUND`；P1 的模块必须显式设置资源级错误码（如 `PROJECT_NOT_FOUND`）。
- P0 没有引入测试框架；上述验证以临时脚本和真实 PostgreSQL 查询完成。
- MinIO 使用 Bitnami legacy 镜像，仅限本地开发。
- 迁移需要手动执行，API 启动不会自动跑迁移。
