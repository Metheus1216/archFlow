# 架构设计与后续演进

> 复查日期：2026-11-13。本文说明设计理由与实施边界。当前实现见[项目说明](./项目说明.md)，任务状态只在[待做清单](./待做清单.md)维护，尚未定稿的设计见[待确认问题](./待确认问题.md)。
> 除明确标注的代码现状外，下述内容是设计要求。字段、格式和枚举以[共享 Zod 定义](../packages/shared/src/schemas/)为准；不熟悉的名称可查[术语说明](./术语说明.md)。

## 1. 第一版部署为一个后端应用

第一版使用 Next.js 前端和 NestJS 后端。Agent 作为公共包由 API 进程直接调用，数据库、缓存与文件存储分别使用 PostgreSQL/pgvector、Redis、MinIO。

| 模块   | 负责的工作                                         | 边界                                                    |
| ------ | -------------------------------------------------- | ------------------------------------------------------- |
| Web    | 页面、画布、客户端状态、请求和接收流式事件         | 不持有模型密钥，不执行服务端工具                        |
| API    | 用户身份和权限、业务数据、文件、任务管理           | 通过 Agent 包执行模型任务                               |
| Agent  | 模型输入、条件提取、资料检索决策、图生成和输出校验 | 不包含 HTTP Controller；数据读写由明确的接口与 API 协作 |
| Shared | 共享数据定义与常量                                 | 先确定数据，再修改调用方                                |
| DB     | 实体和迁移                                         | 不存放业务执行流程，禁止自动同步建表                    |

这样先建立可检查的单进程流程，减少服务通信和部署复杂度。只有资源消耗、故障隔离或发布节奏出现明确差异，并有实际运行数据支持时，才继续拆分。

不引入 LangChain、LangGraph、Vercel AI SDK 或 BullMQ。第一版也不引入 RabbitMQ、Go 解析服务、MCP、API 网关或多人实时协作。

## 2. 数据保存与对话上下文

### 第一版要求

- `agent_states` 每个会话保存一份最新的条件数据与当前步骤；更新时比较版本，避免相互覆盖。
- `conversations.current_draft_graph` 保存当前图，`messages.graph_snapshot` 保存消息对应的关键图。布局保存方式见 [Q-01](./待确认问题.md#q-01-拖拽位置如何保存)。
- 每次模型请求由系统指令、已确认条件、当前图、相关资料和最近消息组成。最近约 10 条消息只是初始策略，仍要检查模型输入长度，不能把条数当作长度保证。
- 第一版不自动摘要，不保存跨会话用户偏好。新条件覆盖旧条件时保留来源和更新时间；发现冲突时追问用户，避免静默修改已确认信息。
- 项目资料检索必须带 `project_id`。复制会话时需要独立初始化条件与图，具体边界见 [Q-07](./待确认问题.md#q-07-分页与复制历史的边界尚需落实)。

这些是实现要求；当前 Agent 状态读写、条件来源结构和上下文组装都尚未实现。

### 后续：长对话摘要

只有历史消息明显影响响应时间、调用量，或固定测试证明最近消息窗口会漏掉关键条件时，再做摘要。预算按单次模型输入长度计算，要预留输出、系统指令、工具定义和当前问题的空间。

摘要应保存已确认条件、被否决方案及原因、未决问题、关键决定、覆盖到的消息位置、版本与用量。结论保留来源消息 ID，原消息继续保存。优先压缩较旧消息，资料片段按相关性筛选，不把资料全文重复塞进摘要。

原方案建议使用独立 `conversation_summaries` 表保留版本，`agent_states` 只关联当前版本；这是候选设计，尚未创建表或 Zod。生成失败时回到截断策略，可关闭或回滚。上线前比较条件保留率、引用正确性、响应时间与调用量。界面可以解释哪些历史已压缩，不展示模型内部思考过程。

后续还可以评估项目决策记忆和跨会话偏好；用户偏好必须获得明确授权，且可查看、删除。历史决定与上传文档应分开检索，避免来源混淆。

## 3. 模型执行流程

外层程序限定执行步骤，模型只在指定步骤内决定是否使用工具。第一版流程为：接收问题 → 提取条件 → 必要时暂停追问 → 查询资料 → 生成图与说明 → 校验并保存 → 完成。

“Workflow 在外，ReAct 在内”在本项目中具体表示：不能把整个任务交给一个无限循环；只有检索等需要探索的步骤，允许模型根据工具结果继续尝试。初始限制为最多 6 轮、8 次工具调用；同一工具以相同参数连续重复时停止。信息足够、预算耗尽或工具连续失败时也必须结束，并给出可解释结果。

### 工具范围

| 工具                      | 用途                   | 执行要求                               |
| ------------------------- | ---------------------- | -------------------------------------- |
| `get_project_constraints` | 读取已确认条件         | 只读、限定当前项目/会话                |
| `retrieve_knowledge`      | 查询本项目文档片段     | 强制项目过滤，返回可追溯来源           |
| `validate_graph`          | 检查图字段和连接关系   | 使用共享图定义；结构通过不等于架构合理 |
| `ask_user`                | 提出需要用户回答的问题 | 保存暂停记录，关闭当前事件流并等待     |

工具参数与结果使用 Zod 定义，并转换成模型接口需要的 JSON Schema。只读操作可直接执行；修改数据或删除等操作应标明风险，涉及用户确认的写入在批准后执行。记录工具名、必要且脱敏的参数、耗时、结果和执行 ID，恢复任务时不能重复执行已有副作用。

第一版先完成澄清卡片。通用操作审批、结果复核及其数据结构在 P1 完善。需要超时、有限重试、幂等和结果长度限制；工具不能绕过权限或图校验。

实现时可按需要采用模型适配、工具注册、上下文处理流水线、数据库事务和事件分发等组织方式，不要求为了套用设计模式增加通用框架。不要使用继承体系组织 Agent，也不要用全局可变单例保存某个用户的任务状态。

## 4. 任务状态与流式回复

发消息接口先保存任务并返回 `202` 和任务 ID，再由独立 GET 接口持续发送事件。浏览器使用 `@microsoft/fetch-event-source`，可以携带认证和重连位置请求头。

数据库保存任务、文字、图、卡片和暂停记录。进程内事件缓存只补发最近事件，任务结束后保留 10 分钟；缓存丢失后用数据库快照恢复显示。

| 事件               | 用户可见效果                          |
| ------------------ | ------------------------------------- |
| `run-start`        | 关联一次任务与助手消息                |
| `status`           | 显示执行阶段                          |
| `text-delta`       | 追加文字；全量恢复时按 `replace` 覆盖 |
| `graph`            | 显示当前生成的图                      |
| `interrupt`        | 显示等待用户输入，关闭当前连接        |
| `done` 与 `[DONE]` | 标记任务结束，重新读取保存结果        |

等待用户时使用 `waiting_input`，它不是终态。暂停保存到 `runs.metadata.interrupt`，默认等待 24 小时，可配置；超时或主动取消进入 `canceled`。恢复沿用原任务和助手消息，使用 `resume: true` 避免清空已显示文字。

暂停请求如何绑定具体暂停点、进程重启后如何处理残留运行任务，尚需完成 [Q-02](./待确认问题.md#q-02-暂停和继续执行的数据还不完整) 和 [Q-03](./待确认问题.md#q-03-进程退出后的未完成任务怎样处理)。网络重连不会终止计算；进程退出会停止计算，二者不能作同一承诺。

以后如果部署多个 API 实例，或把执行移到其他进程，必须把事件缓存改为共享存储，例如 Redis Stream 或数据库事件表；单实例阶段不提前实现。

## 5. 模型与提示词

### 已确定的方向

| 任务                           | 选型方向                         | 当前状态                                 |
| ------------------------------ | -------------------------------- | ---------------------------------------- |
| 主对话、条件提取、图生成、标题 | DeepSeek chat 类模型             | 方向已定，适配与实际调用未实现           |
| 图片理解                       | 千问视觉模型，生成图片文字描述   | 型号和输入限制待验证                     |
| 文本向量化                     | 千问 Embedding 模型              | 必须先验证与数据库向量维度兼容           |
| 深度推理                       | DeepSeek reasoner 类模型         | 后续按需评估，先确认工具与结构化输出能力 |
| 模型质量评分                   | 与生成模型不同的模型配合人工抽查 | 后续建立评分规则                         |

在 `packages/agent/src/llm/` 集中适配，按任务配置模型。记录供应商、模型、提示词版本、调用用量与耗时；不要在各业务文件中分散硬编码型号。当前 `.env.example` 的通用模型变量不足以证明多任务配置已经完成，见 [Q-06](./待确认问题.md#q-06-模型配置和向量维度需要真实验证)。

提示词按角色边界、项目条件、资料片段、近期消息与用户问题分层组织。固定规则和工具定义放在前面，变化内容放在后面。不要把每轮变化的时间或随机值放进固定部分。

约束提取区分用户明确表达与模型推断；图生成负责节点与关系，坐标由前端处理。程序将模型临时 ID 映射成稳定 ID 时，必须同步重写连线引用，不能分别生成无关联的新 ID。

所有模型结果经过共享数据校验。失败时把具体问题交给模型有限次数修正，图最多修复 2 次，仍失败则保存错误并通知用户。Zod 可以拒绝不合格结果，无法保证模型每次输出合法或方案正确。提示词文件要有版本，修改前后运行同一批固定测试。

### 后续：平台预设模型选择

先做平台允许列表，由服务端保存密钥和能力信息，包括工具、结构化输出、图片、流式与输入长度能力。客户端只能选择列表内模型；解析后的配置保存到本次任务，切换只影响新任务。

候选配置层级为任务、项目、用户、系统默认，首版只实现任务覆盖系统默认，避免过多层级。未来偏好可独立存表，不混入 Agent 条件状态。模型不支持当前任务时提前说明；回退模型也记录原选择与原因。

用户自带密钥与自定义服务地址（BYOK）尚未立项，不能与平台模型选择合并实现。若未来支持，需要单独设计密钥加密、不可回读、日志隐藏和访问边界。

## 6. 项目资料检索

### 入库

上传 → 文件校验 → 原文件写 MinIO → 文本提取或图片描述 → 清洗与分段 → 向量化 → 保存片段 → 文件标记 `ready`。

初始切片策略按标题和段落组织，约 400～800 token、重叠约 10%～15%；代码块、表格和相关说明尽量保持完整。片段记录文件、序号、标题层级、原文位置、向量模型与版本信息。参数是待评测的初始策略，不作为 API 字段限制。

图片描述属于第一版范围，应在 P0-17 完成到可检索；P1 再完善质量评测。PDF/DOCX 第一版只保存。入库和查询使用兼容的向量模型与维度，禁止混用旧数据。

### 查询

根据当前问题和已确认条件生成查询向量，始终限定 `project_id` 与可用文件状态。初始可先检索 20～30 个候选，过滤、去重后选约 5～8 段给模型；之后依据测试调整。

第一版只做向量检索。找不到资料时说明没有依据；引用要能追溯到文件和具体片段。HNSW 索引先检索再过滤项目时可能漏掉相关内容，数据量增大后再用测试决定调整检索参数或分区。

后续评测包括：相关片段被找回的比例、相关结果是否排在前面、引用是否支持结论、无资料时是否正确说明。重排序和关键词混合检索只有证明优于当前方案后再引入。

## 7. 权限、错误与运行检查

- 每个业务入口检查资源所有者；越权统一返回 404，不暴露资源是否存在。
- 访问凭证仅在前端内存，刷新凭证使用安全 Cookie。Redis 保存刷新凭证哈希及设备会话状态，轮转和复用吊销范围统一见[认证规范](./API文档/2.%20认证.md)。
- 限定 CORS 来源，Cookie 写请求校验来源，凭证不进入 URL、日志或模型上下文。
- 上传净化文件名，检查大小、允许类型与文件真实性；处理超时和失败要有明确状态。下载通过鉴权 API，支持范围请求和缓存校验。
- 错误 `data` 始终为 `null`，响应不得暴露堆栈、SQL 或内部路径。普通校验状态码与当前实现的差异见 Q-04。
- 为请求、生成任务和模型/工具调用关联 traceId，记录结构化日志。当前实现主要覆盖异常路径，成功请求、204、流式路径和完整日志仍待完成。
- 关注生成成功率、首次输出等待时间、总耗时、用量、工具失败和断线情况。先能从日志或报表查到数据，再评估专用监控平台。

基础测试使用 Vitest，真实接口测试计划使用 Supertest。先覆盖权限、版本冲突、重复提交、流顺序、重连、缓冲失效和暂停恢复，再建立 20～50 条固定模型测试。测试应同时检查图结构、约束保留、引用依据和无资料情形。

后续才接 OpenTelemetry、Prometheus、Grafana，贯穿 HTTP、任务、模型、工具、数据库及异步服务。测试和运行观测不能互相替代。

## 8. 入口代理与生产部署

当前 Next.js middleware 只根据提示 Cookie 跳转，真正鉴权由 API 完成。NestJS 为唯一业务入口，单体阶段不增加 API Gateway 或 BFF。

Nginx 计划承担 HTTPS、请求大小控制、traceId 透传与 SSE 反向代理；流接口要关闭缓冲并设置足够的读取超时。应用 Docker 镜像、Nginx 配置、GitHub Actions 发布流程目前尚未落地，不属于已具备的部署能力。

出现多前端、多服务或明确的流量管理需求后，再评估额外网关。后续 Go 服务只在内网访问，不直接对公网开放。

## 9. 后续：RabbitMQ 与一个 Go 文档解析服务

这项扩展在第一版完成后再做。Node 继续拥有用户权限、业务库、文件状态、切片规则、向量化和项目隔离；Go 只负责文档解析/OCR 等专门计算，不直接写业务数据库。

处理顺序：Node 保存文件并发布解析任务 → Go 从 MinIO 读取并解析 → 把文本或结构化产物写回 MinIO → 发布完成/失败通知 → Node 切片、向量化、更新状态。

队列只传文件标识、版本、产物位置等元数据，不传文件内容。沿用 `document.parse.requested`、`document.parse.completed`、`document.parse.failed` 的事件命名方向；消息格式由 Zod 转 JSON Schema 供两种语言校验。

需要按文件和版本防重复处理、确认/拒绝消息、有限重试、死信队列、消费并发限制、待发送消息记录和 traceId 透传。队列名、消息版本、重试参数和 Go 目录仍属未定设计。

优先接 PDF/DOCX/大图 OCR，文本和 Markdown 暂留 Node。服务稳定后再决定是否统一迁移其他解析。未来异步任务统一用 RabbitMQ，不引入 BullMQ，也不据此拆分整个业务后端。

## 10. 后续：外部工具与可复用任务配置

### MCP

MCP 是外部工具接入协议。未来客户端可连接代码托管、事项管理等系统，转换为内部工具；服务端模式可向其他工具开放项目、图和资料。两种方向都要处理鉴权、隔离、超时、重连与工具名称冲突。

外部返回内容按资料处理，不能让其指令覆盖系统规则。当前没有 MCP 产品实现。

### Skill

Skill 是可复用的提示词、工具允许列表、输出定义和模型配置组合。它与 MCP 工具来源不同，也与仓库里的开发辅助技能不同。当前侧栏按钮没有业务实现。

若立项，沿用三层候选设计：项目定义保存不可变版本；会话显式绑定版本；创建任务时保存实际使用配置的快照。优先级为本次任务覆盖、会话绑定、项目默认。修改定义生成新版本，历史任务不随当前版本变化。

Skill 只能缩小工具权限，不能绕过人工确认或输出校验。项目提示片段不提升为系统规则。候选资源为项目 Skill 管理和会话绑定接口；先定义 Zod 再开发，当前不建立相关表或端点。

## 11. 开发顺序与重新评估条件

先完成账号与项目数据，再完成画布保存，之后接入模型生成、方案保存和资料检索。每步同时补权限、异常路径与验证；任务及依赖见[待做清单](./待做清单.md)。

第一版之后先做质量评测和安全完善，再做文档解析服务，最后按实际需求评估模型选择、摘要、Skill、MCP 等扩展。继续拆服务前，需要证明独立的计算资源、故障隔离、数据归属或发布节奏确实能带来收益。
