# 工作台首屏优化记录（2026-11-11）

## 结论

本次处理两个独立问题：

1. **首屏被项目树阻塞**：`app/workspace/layout.tsx` 在 layout 顶层 `await listProjectNodes()`，导致右侧 `page.tsx` 也无法输出。改为把项目树查询移进 `<Suspense>` 内的异步组件，layout 同步渲染，page 先流式输出，侧栏用骨架占位。
2. **客户端重复做 Zod 校验**：`lib/api-client.ts` 对每个响应执行 `ApiResponseSchema(schema).parse()`，hooks 静态传入实体 schema，导致 zod（含全部 locale）进入客户端首屏。改为只校验响应外壳，实体类型由泛型声明；服务端校验保持不变。

结果：dev `/workspace` 首屏 JS 7,568,207 B → 5,954,998 B（-21.3%），zod chunk 归零；production `/workspace` First Load JS 185 kB。

## 1. 问题一：项目树阻塞首屏

### 1.1 改前

`apps/web/app/workspace/layout.tsx`：

```tsx
const WorkspaceLayout = async ({ children }: { children: ReactNode }) => {
  const projects = await listProjectNodes();

  return (
    <ResizablePanelGroup direction="horizontal" ...>
      <ResizablePanel ...>
        <Sidebar projects={projects} />
      </ResizablePanel>
      <ResizableHandle />
      <ResizablePanel ...>{children}</ResizablePanel>
    </ResizablePanelGroup>
  );
};
```

`layout` 是 async 组件，Next.js 必须等它 resolve 才能提交任何 HTML/RSC 数据。因此 `children`（`page.tsx` 中的会话、消息查询）即使已经就绪，也只能排队等待项目树。

### 1.2 改后

`layout.tsx` 保持同步，项目树查询下沉到 `SidebarSection`：

```tsx
const SidebarSection = async () => {
  const projects = await listProjectNodes();

  return <Sidebar projects={projects} />;
};

const WorkspaceLayout = ({ children }: { children: ReactNode }) => (
  <ResizablePanelGroup ...>
    <ResizablePanel ...>
      <Suspense fallback={<SidebarSkeleton />}>
        <SidebarSection />
      </Suspense>
    </ResizablePanel>
    <ResizableHandle />
    <ResizablePanel ...>{children}</ResizablePanel>
  </ResizablePanelGroup>
);
```

生效原因：

- layout 同步返回元素树，Next 可以立即提交外层 shell；
- 项目树查询由最近的 `<Suspense>` 捕获，先提交 `SidebarSkeleton`；
- 数据到达后，React 用真实侧栏替换 fallback；
- `page.tsx` 不在这个 Suspense 内，输出不被项目树阻塞。

`export const dynamic = "force-dynamic"` 保留：工作台数据按用户/会话变化，不能静态化；它不影响 Suspense 流式输出。

### 1.3 骨架组件

新增 `apps/web/components/workspace/sidebar/sidebar-skeleton.tsx`：

- 按 `Sidebar` 的品牌区、两个按钮、列表行高度做占位，避免数据到达时布局跳动；
- 使用 `aria-busy="true"` 和 `aria-label="项目列表加载中"` 暴露加载状态；
- 纯展示组件，没有 `"use client"`，不增加客户端模块。

### 1.4 为什么不用 `loading.tsx`

`app/workspace/loading.tsx` 会在导航时替换整个 page 区域，右侧聊天/画布也会一起进入整页 loading。本问题只需要延迟侧栏，Suspense 粒度更小，且能保留 `page.tsx` 的服务端预取。

## 2. 问题二：客户端重复 Zod 校验

### 2.1 改前

`apps/web/lib/api-client.ts`：

```ts
export const requestApi = async <T>(
  path: string,
  schema: z.ZodType<T>,
  init?: RequestInit,
): Promise<T> => {
  const response = await fetch(path, { ...init, headers });
  const payload: unknown = await response.json();
  const envelope: ApiResponse<T> = ApiResponseSchema(schema).parse(payload);

  if (envelope.code !== ERROR_CODES.OK || envelope.data === null) {
    throw new ApiError(envelope.code, envelope.message, envelope.errors);
  }

  return envelope.data;
};
```

hooks 的调用方式：

```ts
requestApi(`/api/mock/conversations/${id}`, Conversation)
requestApi(`/api/mock/conversations/${id}/messages?...`, messagePageSchema)
requestApi("/api/mock/projects", projectPageSchema)
```

`Conversation`、`PageSchema(Message)`、`PageSchema(ProjectNode)` 都是运行时值，不是 `type`，所以整个 `@arch-flow/shared` 和 zod 都会进入 client bundle。

### 2.2 为什么 zod 会全量进入 dev

`zod` 的入口链是 `index.js` → `v4/classic/index.js` → `external.js`，其中：

```js
export * as locales from "../locales/index.js";
```

Turbopack dev 不做生产级 tree-shaking，`locales` 命名空间被完整保留，几十个语言包全部进入 dev chunk。实测三个 chunk：

| chunk | 大小 |
| --- | --- |
| `b6b38_zod_v4_core` | 694,073 B |
| `b6b38_zod_v4_locales` | 547,240 B |
| `b6b38_zod_v4_classic` | 319,796 B |

合计 1,561,109 B。生产构建会摇掉未使用的导出，所以线上没有这块开销；但 dev 首屏和本地调试会真实加载。

### 2.3 改后

`api-client.ts` 只保留外壳校验：

- `parseEnvelope`：检查 `code`/`message`/`traceId` 为 `string`，`data` 字段存在；不符合抛 `Error("服务端响应不符合 ApiResponse 契约")`；
- `parseFieldErrors`：逐项检查 `field`/`code`/`message`，格式不对的项直接丢弃；
- `readEnvelope`：处理非法 JSON，抛 `Error("服务端返回了非法 JSON（HTTP ...）")`；
- `requestApi<T>(path, init?)`：校验 `code === "OK"` 且 `data !== null`，返回 `envelope.data as T`。

新的函数体（省略 header 处理）：

```ts
export const requestApi = async <T>(
  path: string,
  init?: RequestInit,
): Promise<T> => {
  const response = await fetch(path, { ...init, headers });
  const envelope = await readEnvelope(response);

  if (envelope.code !== ERROR_CODES.OK || envelope.data === null) {
    throw new ApiError(envelope.code, envelope.message, envelope.errors);
  }

  return envelope.data as T;
};
```

hooks 改动：

| 文件 | 改前 | 改后 |
| --- | --- | --- |
| `use-conversation.ts` | `requestApi(url, Conversation)` | `requestApi<Conversation>(url)`，`import type` |
| `use-messages.ts` | `PageSchema(Message)` 作为参数 | `requestApi<Page<Message>>(url)` |
| `use-projects.ts` | `PageSchema(ProjectNode)` / `ProjectNode` 作为参数 | `requestApi<Page<ProjectNode>>` / `requestApi<ProjectNode>` |
| `use-send-message.ts` | `requestApi(url, MockSendMessageResult, init)` | `requestApi<MockSendMessageResult>(url, init)` |
| `use-create-conversation.ts` | `requestApi(url, Conversation, init)` | `requestApi<Conversation>(url, init)` |
| `use-rename-conversation.ts` | `requestApi(url, Conversation, init)` | `requestApi<Conversation>(url, init)` |
| `use-delete-project-items.ts` | 已使用 `requestApiVoid` | 无改动 |

### 2.4 服务端没有放松

- mock 路由：`mockOk(schema, data)` 在返回前执行 `ApiResponseSchema(schema).parse(...)`，不合法直接抛错；
- 真实 API：Controller 入参继续走 `ZodValidationPipe`；
- `packages/shared` 仍是唯一 schema 源；客户端只通过 `import type` 取类型，没有手写 interface；
- `ApiResponse` 的字段约束没有改，只是客户端不再对 `data` 内部逐字段 parse。

### 2.5 画布数据

改前 `apps/web/lib/mock-graph.ts`：

```ts
import { MockGraph, type Graph } from "@arch-flow/shared";

export const parseMockGraph = (graph: Graph | null): MockGraph | null => {
  if (!graph) {
    return null;
  }

  const parsed = MockGraph.safeParse(graph);

  return parsed.success ? parsed.data : null;
};
```

改后用手写结构守卫：

- `nodes` / `edges` 必须是数组；
- node 的 `id`/`kind`/`eyebrow`/`label` 为 `string`，`meta` 为 `string | null`，`left`/`top` 为 `number`；
- edge 的 `id`/`path` 为 `string`。

边界说明：守卫不校验 `kind` 是否属于枚举、不校验 `left`/`top` 是否在 0–100，这两项由服务端 `MockGraph` schema 保证；守卫只负责“脏数据不把渲染打崩”。核心代码：

```ts
const isMockGraphNode = (value: unknown): value is MockGraphNode =>
  isRecord(value) &&
  typeof value.id === "string" &&
  typeof value.kind === "string" &&
  typeof value.eyebrow === "string" &&
  typeof value.label === "string" &&
  (value.meta === null || typeof value.meta === "string") &&
  typeof value.left === "number" &&
  typeof value.top === "number";

export const parseMockGraph = (graph: Graph | null): MockGraph | null => {
  if (
    !graph ||
    !Array.isArray(graph.nodes) ||
    !Array.isArray(graph.edges) ||
    !graph.nodes.every(isMockGraphNode) ||
    !graph.edges.every(isMockGraphEdge)
  ) {
    return null;
  }

  return { nodes: graph.nodes, edges: graph.edges };
};
```

渲染层同时加了兜底：

```tsx
const Icon = NODE_ICONS[node.kind] ?? Workflow;
```

未知 `kind` 显示通用图标，不再因为 `NODE_ICONS[kind]` 为 `undefined` 导致 React 渲染崩溃。

### 2.6 shared 子路径导出

改前 `api-client.ts` 从 `@arch-flow/shared` 导入 `ERROR_CODES`。该入口是 barrel，会重新导出所有 schema 模块，即使只用一个常量也会把 zod 拉进来。

`packages/shared/package.json` 新增：

```json
"./constants/error-codes": {
  "types": "./dist/constants/error-codes.d.ts",
  "import": "./dist/constants/error-codes.js"
}
```

客户端改为：

```ts
import { ERROR_CODES } from "@arch-flow/shared/constants/error-codes";
```

shared 需要重新执行 `pnpm --filter @arch-flow/shared build` 生成 `dist`，否则子路径解析不到。

## 3. 方案取舍

### 3.1 为什么保留响应外壳校验

完全去掉校验会丢失错误码和错误信息，`ApiError` 无法构造，toast 也无法给出可操作提示。外壳校验成本只有几十行且无依赖，能覆盖 4xx/5xx、网关返回 HTML、代理错误页等情况。

### 3.2 为什么不用 `zod/mini` 或 deep import

- `zod/mini` 的 API 与 classic 不同（`z.string().min(1)` vs `z.string().check(z.minLength(1))`），需要重写 `packages/shared` 全部 schema 并同步 API 端，回归面远大于收益；
- deep import `zod/v4/classic/*` 仍会经过 `external.js` 的 `export * as locales`（`z` 命名空间由 `index.js` 组装），绕不开语言包；
- 只把 `MockGraph` 改成 deep import 省不掉 zod 核心，因为 hooks 仍在用实体 schema。

### 3.3 为什么不做动态 import

`requestApi` 在页面挂载后立即被 React Query 调用，动态 import 只是把 1.5MB 从 HTML 阶段挪到 hydration 后几百毫秒，网络字节不变，还多一层异步与 loading 状态。

### 3.4 为什么不动 Radix / Next dev runtime

- lucide 已按需加载（首屏只出现实际用到的图标）；
- Radix 虽然通过 barrel 导入，但 Turbopack 已只保留 dialog/dropdown-menu 及其依赖（24 个 Radix 包），`optimizePackageImports` 没有额外收益；
- 剩余约 1.1MB 是弹窗/菜单运行时，要省只能把 Dialog/DropdownMenu 改成受控的懒加载，交互和无障碍复杂度高，暂不做；
- Next dev runtime 约 3.5MB（devtools 1.5MB、react-dom dev 0.9MB、next client 0.55MB 等），属于框架成本，业务代码无法削减。

## 5. 影响面与回退

### 5.1 行为变化

- `requestApi` 签名从 `(path, schema, init?)` 变为 `(path, init?)`，所有调用方已更新，TypeScript 会阻止漏改；
- 实体字段不符合 schema 时，不再在 fetch 阶段抛 `ZodError`，而是继续使用数据，可能到渲染阶段才暴露；外壳不符合契约仍抛 `Error`；
- 非法 JSON 的异常从原生 `SyntaxError` 变为带 HTTP 状态的可读 `Error`；
- 画布守卫比 Zod 宽松：未知 `kind`、越界坐标不会拒绝整张图；未知 `kind` 用通用图标兜底。

### 5.2 风险

- 如果未来接入第三方或不可控 API，客户端缺少实体校验会放大脏数据影响；届时可按 5.3 回退，或只对第三方接口单独加校验；
- `envelope.data as T` 是类型断言，正确性依赖服务端契约，代码注释已说明。

### 5.3 回退步骤

1. `api-client.ts`：给 `requestApi` 加回 `schema: z.ZodType<T>` 参数，恢复 `ApiResponseSchema(schema).parse(payload)`；
2. hooks：恢复 schema 的运行时导入并作为第二参数传入；
3. `mock-graph.ts`：恢复 `MockGraph.safeParse`；
4. 可选：移除 shared 的 `./constants/error-codes` 导出，改回 barrel 导入；
5. 执行 `pnpm --filter @arch-flow/shared build`。

回退后 dev 首屏会回到约 7.57MB。
