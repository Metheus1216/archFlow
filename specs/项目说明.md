# ArchFlow 项目说明

> 核查日期：2026-11-13。
> 本文依据当前仓库的页面、接口入口、共享数据定义、数据库迁移和测试编写。持续更新的任务状态见[待做清单](./待做清单.md)；本次核查与验证结果见[文档审计记录](./问题记录/2026-11-13-项目文档审计与整理.md)。

## 1. 项目要解决什么问题

ArchFlow 帮助缺少架构设计经验的学生和独立开发者，把项目需求整理成有依据、能够调整和保存的技术方案。

用户通常知道自己要做一个什么产品，却不一定知道应该选哪些组件、如何划分职责、哪些复杂度暂时不值得承担。ArchFlow 计划通过对话补齐这些信息，再结合项目资料生成架构说明和架构图。

例如，用户提出“做一个面向学校社团的活动报名系统”。助手需要先确认预计人数、开发团队、交付时间、部署预算、数据安全要求，再据此解释服务和存储方案。团队只有两人、交付时间很短，与已有专职运维团队的情况，应得到不同建议。

产品的主要价值在于：让技术选择对应具体需求，并保留选择依据，方便用户继续修改方案。

## 2. 用户最终会怎样使用

第一版计划支持以下完整过程：

1. 注册、登录并创建项目。一个项目集中保存相关会话、文件和架构方案。
2. 描述产品想法。助手追问团队规模、预算、访问量等会影响技术选择的条件。
3. 回答选择卡片或直接补充文字。已经确认的条件保存在数据库中。
4. 助手查询本项目已处理的资料，生成方案说明、引用来源和架构图。
5. 用户在画布上调整图，保存草稿；遇到同时修改时提示版本冲突。
6. 把满意的图保存为命名方案，即文档所称的“架构资产”。
7. 需要比较另一种方案时，从历史消息复制出独立会话，保留原来的讨论。

完整范围和验收条件见 [MVP 需求边界](./mvp.md)。这里描述的是目标使用方式，当前代码尚未支持全部步骤。

### 当前演示容易产生的误解

- 开发登录只写一个用于页面跳转的 Cookie，不验证邮箱或密码；生产模式的登录提交还没有实现。
- 新建模拟项目会自动放入示例文件和示例资产，它们不是上传、解析或生成的成果。
- 工作台页面在服务端直接读取模拟数据。以后接真实接口时，还要修改这条读取路径，不能只替换浏览器请求地址。
- “自动布局”“保存资产”等控件的出现，以及依赖中已经安装 React Flow、Dagre、OpenAI SDK，都不能作为功能完成证据。
- 前端 SSE 客户端和 Agent 引擎文件目前只有待实现说明。

## 4. 系统各部分怎样配合

仓库采用一个仓库管理多个应用和公共包的方式。第一版后端部署为一个 NestJS 应用，模型执行逻辑在同一进程中调用。

| 目录              | 负责什么                                                       | 这样划分的原因                         |
| ----------------- | -------------------------------------------------------------- | -------------------------------------- |
| `apps/web`        | 页面、画布交互、浏览器状态、HTTP 请求、接收流式回复            | 让用户交互与模型执行分开维护           |
| `apps/api`        | 登录与权限、业务接口、数据库操作、文件存储、创建和管理生成任务 | 由服务端统一控制用户数据和任务生命周期 |
| `packages/agent`  | 组装模型输入、提取条件、查询资料、调用工具、生成和校验图       | 把与模型有关的逻辑集中在一个位置       |
| `packages/shared` | 用 Zod 定义跨模块交换的数据，并推导 TypeScript 类型            | 前后端使用同一份字段与校验规则         |
| `packages/db`     | 数据库实体和迁移                                               | 数据结构变更可记录、可重复执行         |

PostgreSQL 保存账号、会话、消息、图、任务与约束条件；pgvector 保存和检索文档片段的语义向量。Redis 计划用于登录凭证状态和限流。MinIO 保存上传文件的原始内容。

核心代码直接使用模型 SDK 和明确的流程控制，不引入 LangChain、LangGraph 或 Vercel AI SDK。主要目的是能直接检查每次模型请求、工具调用、暂停和数据保存发生在哪里。

## 5. 当前最需要补齐什么

### 真实账号与业务数据

先完成注册、登录、刷新、退出，再让项目、会话和消息走真实 API。每条数据操作都要检查所有者，不能沿用模拟环境的全局文件数据。

### 可保存的画布

把示例展示替换成 React Flow 交互，接入草稿保存和版本冲突处理。开始前需要解决一个明确的设计缺口：现有图定义不保存坐标，却要求刷新后保留拖拽布局。建议把节点位置作为独立布局数据定义，具体字段先在共享 Zod 中确定，见[待确认问题 Q-01](./待确认问题.md#q-01-拖拽位置如何保存)。

### 实际模型执行与回复传输

实现模型连接、条件提取、图生成、运行状态保存以及服务端流式事件。模型输出必须经过校验；校验失败可有限次数修复，仍不合格就明确失败，不能承诺模型始终返回合法数据。

浏览器断线只影响接收，生成任务继续运行。用户重连后先补发缓存事件；缓存失效则读取数据库中的任务和消息恢复显示。服务器进程退出后是否继续计算，是另外的恢复策略，不能与网络重连混为一谈。

### 项目资料与方案保存

完成文件上传、文本处理和图片理解，再让助手检索当前项目的资料。支持保存命名方案、恢复历史图和复制会话。图片处理属于既有第一版范围；PDF/DOCX 第一版只保存文件，不读取其内容。

## 6. 后面按什么顺序做

| 顺序 | 工作                                                             | 完成后必须能演示                                       |
| ---- | ---------------------------------------------------------------- | ------------------------------------------------------ |
| 1    | 补齐影响实现的数据定义；复核增量迁移；完善健康检查和接口测试入口 | 图、暂停和错误处理的规则一致；数据库迁移有执行证据     |
| 2    | 真实认证、项目和会话接口，替换相关模拟请求                       | 新用户登录后创建项目和会话，刷新后仍属于该用户         |
| 3    | 交互画布、布局保存、草稿版本检查                                 | 调整图后保存并刷新；两个窗口冲突时不会覆盖他人的修改   |
| 4    | 模型连接、条件提取、生成任务、流式输出、卡片暂停与继续           | 描述需求 → 回答追问 → 得到说明和架构图；断线可恢复显示 |
| 5    | 架构资产、历史图恢复、复制历史会话                               | 保存命名方案、切换查看，从同一历史位置比较不同方案     |
| 6    | 文本/图片处理、项目内检索、引用来源                              | 上传资料后回答有依据；其他项目的内容不会被检索出来     |
| 7    | 清理模拟入口，完成错误路径、安全和整体验收                       | 不依赖开发登录与示例数据，完成全部第一版用户场景       |

权限、错误处理和相应测试应随每步一起完成。最后一步负责整体验收，不能把这些要求全部拖到最后。具体任务编号和依赖以[待做清单](./待做清单.md)为准。

## 7. 哪些能力以后再考虑

第一版完成后，先积累固定的测试问题，检查条件提取是否正确、图是否可用、引用是否支持结论、响应时间和调用成本是否可接受。质量问题有了数据，再决定优化方案。

PDF/DOCX 解析计划以后使用一个 Go 服务，通过 RabbitMQ 接收任务。用户选择平台预设模型、长对话摘要、外部工具接入和可复用任务配置也属于后续扩展，都有单独的立项条件。当前侧栏中的 Skill 入口不代表这些功能已经存在。
