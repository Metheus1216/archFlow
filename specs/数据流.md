# 用户操作与数据流

> 本文描述第一版的目标处理流程，尚未接通的功能见[待做清单](./待做清单.md)。请求字段以[共享 Zod 定义](../packages/shared/src/schemas/)为准；代码名词解释见[术语说明](./术语说明.md)。
> 业务接口使用 `/api/v1` 前缀，健康检查使用根路径。对外 `id` 来自数据库的 `uuid`，内部自增主键不返回给前端。

## 1. 登录与自动续期

1. 用户提交注册或登录请求。服务端返回 `accessToken`，并通过 `Set-Cookie` 保存 `refreshToken`；Redis 保存刷新凭证的哈希及有效期。
2. 前端把访问凭证保存在内存，请求时加 `Authorization: Bearer <accessToken>`。Cookie 由浏览器按规则携带，前端不能读取其中的刷新凭证。
3. 页面刷新后，先尝试刷新接口恢复内存中的访问凭证，再查询当前用户。刷新失败则清除页面登录提示并跳转登录。
4. 普通请求收到 `401 TOKEN_EXPIRED` 时，前端统一发起一次刷新；同时失败的其他请求等待结果，之后最多重发一次。禁止每个失败请求分别刷新。

浏览器中用于页面跳转的“会话提示 Cookie”不承担权限判断。真实权限检查始终在 API 中进行。

## 2. 打开工作台

1. 查询当前用户，再请求 `GET /api/v1/projects` 获取项目及侧栏所需的简要信息。
2. 没有项目时显示创建引导；有项目时根据服务端返回的 `lastActiveConversationId` 选择会话。用户显式选择了会话时优先使用该选择。
3. 没有可用会话则提供创建入口，不向包含空 ID 的地址发请求。
4. 分别获取会话详情和消息列表。详情包含当前草稿和版本，消息按页加载。

当前页面在 Next.js 服务端直接读取模拟文件。接真实后端时，这条服务端读取路径和浏览器请求都需要调整，并保证每次读取携带当前用户身份。

## 3. 创建项目和会话

1. 前端提交 `POST /api/v1/projects`，同一次操作的重试复用同一 `Idempotency-Key`。
2. 创建成功后，再提交 `POST /api/v1/projects/:projectId/conversations` 创建首个空会话。
3. 两步均成功后进入该会话。如果项目已创建而会话创建失败，提示重试创建会话，不再次创建项目。

真实接口不会自动生成模拟环境中的示例文件和示例架构资产。

## 4. 发消息、生成回复和更新图

1. 如果有未保存的图，先保存草稿；版本冲突时先处理冲突，不继续用过时草稿发起生成。
2. 提交 `POST /api/v1/conversations/:conversationId/messages`。服务端校验权限、重复请求和会话是否已有任务，保存用户消息、助手占位消息和 `runs` 记录，返回 `202` 及 `runId`、`streamUrl` 等字段。
3. 前端使用 `@microsoft/fetch-event-source` 连接返回的流地址，携带认证请求头。不能使用原生 `EventSource`，不能把凭证放在 URL 中。
4. 收到 `run-start` 时把任务和助手消息关联。后续 `status` 表示执行阶段，`text-delta` 追加回复，`graph` 替换图，引用、标题与用量事件更新对应界面。
5. 服务端生成期间定期把已生成文字写入 `messages.content`，关键图和卡片也需要保存。内存事件缓存仅用于补发，不代替数据库。
6. 正常完成、失败或取消后发送 `done`，再发送 `[DONE]` 并关闭连接。客户端用消息查询接口读取最终保存结果，按消息 ID 合并，不重复插入。

`queued` 只表示已受理、尚未开始执行，不意味着使用了消息队列。第一版在 API 进程内调度。

## 5. 条件卡片、暂停与继续

1. 助手缺少必要信息时，保存 `message.metadata.card` 与 `runs.metadata.interrupt`，把任务改为 `waiting_input`。
2. 服务端发送卡片和 `interrupt` 事件后关闭当前连接；不发送结束事件。前端显示“等待回答”，不把暂停算成成功或失败。
3. 用户提交卡片答案，或用普通消息补充信息。服务端确认对应暂停点、保存回答，再继续原任务。
4. 恢复后 `run-start` 带 `resume: true`，继续使用原 `runId` 与 `assistantMessageId`。前端保留已有文字，已执行的写入操作不能重复执行。
5. 已回答卡片再次提交时重放首次结果，不再触发推理。前端先更新显示，之后以重新获取的消息为准；提交失败时恢复可操作状态。
6. 暂停记录超过等待期限或用户取消后，任务进入取消状态。重连等待中的任务时，先恢复消息和卡片，再重放暂停事件并关闭连接。

第一版实现澄清卡片；操作审批和结果复核属于后续完善。暂停 `payload`、恢复请求如何绑定暂停 ID、恢复响应中的消息 ID 含义仍需补齐，见[Q-02](./待确认问题.md#q-02-暂停和继续执行的数据还不完整)。

## 6. 网络断开与服务器重启

| 情况                         | 服务端处理                                    | 前端处理                                                |
| ---------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| 浏览器网络断开，API 仍在运行 | 继续执行并保存文字及任务状态                  | 使用已知 `runId` 重连，带上已收到的 `Last-Event-ID`     |
| 内存中仍有事件               | 从确认位置的下一帧补发，再继续实时发送        | 按帧 ID 去重；不要把同一段文字追加两次                  |
| 事件缓存失效，任务仍在执行   | 从数据库发全量消息快照，然后继续实时发送      | `text-delta.replace: true` 表示覆盖文字；正常增量再追加 |
| 任务正在等待回答             | 先补足显示所需数据，再发送 `interrupt` 并关闭 | 恢复卡片，保持等待状态，不自动反复重连                  |
| 任务已结束                   | 恢复保存内容并发送对应结束事件                | 刷新消息列表，结束接收                                  |
| API 进程退出                 | 实际计算已停止；必须按重启策略修正未完成任务  | 先查询任务，不把数据库里残留的 `running` 当作仍在计算   |

事件在任务结束后保留 10 分钟，进程重启会丢失。连续重连失败可改为定期查任务状态；查到等待输入时恢复卡片并停止轮询，查到终态时刷新消息。

“恢复显示”与“继续计算”是两个要求。进程重启后的继续或失败策略尚待确定，见[Q-03](./待确认问题.md#q-03-进程退出后的未完成任务怎样处理)。

## 7. 编辑与保存画布

1. 拖拽等操作先更新本地状态；停止操作 3 秒后提交保存。
2. `PUT /api/v1/conversations/:conversationId/draft` 使用 `SaveDraftInput`，携带图和客户端的 `baseVersion`。
3. 服务端必须用一次有条件的更新比较版本并保存。成功返回新版本；不一致则返回 `409 DRAFT_VERSION_CONFLICT`，错误响应 `data: null`。
4. 冲突后前端保留未保存的编辑，并重新获取服务端会话供用户决定；不能直接把本地旧图用新版本号再提交。
5. 图过大返回 `413 GRAPH_TOO_LARGE`；结构、引用或深度不合法返回 `422 GRAPH_INVALID`。草稿和资产按同样原因区分错误。

布局数据如何随草稿保存仍需先解决 [Q-01](./待确认问题.md#q-01-拖拽位置如何保存)。目前只提交 `Graph` 不能保存拖拽位置。

## 8. 保存命名方案与查看历史

保存架构资产时提交名称与图。列表只加载名称等基本信息，点击某项再请求带图的详情，减少重复传输。

恢复历史图时，前端先读取对应消息的 `graphSnapshot`，有未保存编辑时提示处理，再通过草稿保存接口写入；同样要处理版本冲突。没有快照的消息不能直接宣称可还原该时刻画布。

复制历史会话使用 `/fork` 接口，新建会话并复制选定消息及之前记录，重新建立消息标识及相关引用。新会话草稿、条件状态的初始化细则见[Q-07](./待确认问题.md#q-07-分页与复制历史的边界尚需落实)。

## 9. 文件上传、处理、查询和删除

1. 使用 `multipart/form-data` 上传 `file`。服务端检查所有者、文件类型与大小，保存 MinIO 对象和数据库记录。
2. 文本与图片进入 `processing`。文本提取并分段；图片由视觉模型生成描述。相关内容向量化并保存成功后才进入 `ready`，失败则进入 `failed` 并提供可展示的原因。
3. PDF/DOCX 直接进入 `stored`，界面说明“仅存储，暂不解析”，不进入处理轮询或检索。
4. 前端对仍在处理的文件调用批量状态接口，逐渐延长查询间隔；处理完成、失败、切换页面或取消后停止轮询。
5. 查询资料时同时限定 `project_id` 与可用文件状态。下载经鉴权 API 转发，删除同时考虑数据库记录、切片和 MinIO 对象清理。

实际模型、向量维度及删除失败补偿方式见[待确认问题](./待确认问题.md)。第一版不引入 PDF/DOCX 解析服务或消息队列。
