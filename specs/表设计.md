# 数据库存储说明

> 复查日期：2026-11-13。实际列定义、索引和外键以[实体](../packages/db/src/entities/)及[迁移](../packages/db/src/migrations/)为准；接口字段以共享 Zod 为准。本文解释存储用途，不重复接口长度和枚举限制。
> 初始 9 表迁移有[历史真实执行记录](./问题记录/2026-11-11-后端P0基础设施落地.md)；新增 `runs.metadata`、`agent_states.version` 的迁移已编写，尚缺真实库复核证据。业务接口和状态更新逻辑尚未实现。

## 1. 标识、时间和结构化数据

7 张对外资源表共用以下列；`documents_chunks`、`agent_states` 当前是内部表，没有 `uuid`，与“所有表包含 UUID”的项目规则存在差异，见[Q-05](./待确认问题.md#q-05-内部表的-uuid-与项目规则不一致)。

| 列           | 数据库类型           | 实体表示 | 用途                           |
| ------------ | -------------------- | -------- | ------------------------------ |
| `id`         | 自增 BIGINT          | `string` | 主键及表间关联；不返回给客户端 |
| `uuid`       | UUID，唯一、自动生成 | `string` | API 对外 `id` 的来源           |
| `created_at` | TIMESTAMPTZ          | `Date`   | 创建时间                       |
| `updated_at` | TIMESTAMPTZ          | `Date`   | 最后修改时间                   |

BIGINT 经 PostgreSQL 驱动通常以字符串读取，不能把内部标识转成 JavaScript 数字。文件大小使用已有转换器转为数值。

JSONB 用于保存图、消息附加数据、条件和任务状态。实体中暂以 `Record<string, unknown>` 表示存储对象，业务入口仍需使用共享 Zod 校验，不能直接把数据库对象当作合法接口结果。

## 2. 用户与项目

### `users`：账号

| 列              | 类型          | 含义                                                          |
| --------------- | ------------- | ------------------------------------------------------------- |
| `email`         | VARCHAR，唯一 | 登录邮箱；写入和比较前去两端空白并转小写                      |
| `username`      | VARCHAR       | 显示昵称，可重复                                              |
| `password_hash` | VARCHAR       | 密码哈希，不保存明文，不返回接口；bcrypt 使用在认证实现时接入 |
| `avatar_url`    | VARCHAR，可空 | 头像地址                                                      |

刷新凭证计划保存到 Redis，不建数据库 Token 表。当前尚无注册或登录写入逻辑。

### `projects`：一个用户的项目

| 列             | 类型          | 含义                    |
| -------------- | ------------- | ----------------------- |
| `user_id`      | BIGINT 外键   | 所有者，对应 `users.id` |
| `project_name` | VARCHAR       | API 中的 `name`         |
| `description`  | VARCHAR，可空 | 项目说明                |

每个项目第一版只有一个所有者。查询业务数据前，需要从项目校验当前用户，不能仅凭客户端传入的项目 ID 放行。

## 3. 会话、消息与图

### `conversations`：讨论上下文与当前草稿

| 列                    | 类型        | 含义                                            |
| --------------------- | ----------- | ----------------------------------------------- |
| `project_id`          | BIGINT 外键 | 所属项目                                        |
| `title`               | VARCHAR     | 会话标题                                        |
| `current_draft_graph` | JSONB，可空 | 当前图，对外映射为 `draftGraph`                 |
| `draft_version`       | INT，默认 0 | 草稿版本；保存必须比较 `baseVersion` 后增加版本 |

草稿覆盖保存，历史关键图另外存到消息。当前图定义不保存位置，布局存储需先解决 [Q-01](./待确认问题.md#q-01-拖拽位置如何保存)。

### `messages`：文字、卡片、引用与关键图

| 列                | 类型        | 含义                                         |
| ----------------- | ----------- | -------------------------------------------- |
| `conversation_id` | BIGINT 外键 | 所属会话                                     |
| `role`            | VARCHAR     | 消息角色，含义由 `MessageRole` 定义          |
| `content`         | TEXT        | 消息文字；生成中分批保存，最终写入完整结果   |
| `metadata`        | JSONB，可空 | 消息附加数据，业务结构使用 `MessageMetadata` |
| `graph_snapshot`  | JSONB，可空 | 此消息关联的关键图，用于恢复历史和复制会话   |

卡片随 `metadata.card` 保存，不另建卡片表。直接打字也可能回答问题，因此服务端仍要同步卡片和条件状态；放在同一消息里不会自动解决一致性问题。

`Conversation.draftGraph`、`Message.graphSnapshot` 当前共享定义仍用 `LooseGraph` 兼容旧模拟图。新提交使用 `GraphInput`；切换画布时需要统一读写结构，不能长期并存两套图。

### `assets`：用户明确保存的命名图

| 列           | 类型        | 含义                                       |
| ------------ | ----------- | ------------------------------------------ |
| `project_id` | BIGINT 外键 | 所属项目                                   |
| `name`       | VARCHAR     | 保存名称，可在项目内重名                   |
| `graph_data` | JSONB       | 经共享图规则校验的数据，对外字段为 `graph` |

数据库保存的是业务图结构，不能直接称为 React Flow 组件内部对象。列表不返回图，详情按请求需要加载。

## 4. 文件与检索片段

### `knowledge_base`：上传文件记录

| 列                       | 类型        | 含义                                                 |
| ------------------------ | ----------- | ---------------------------------------------------- |
| `project_id`             | BIGINT 外键 | 所属项目                                             |
| `file_name`              | VARCHAR     | 净化后的原始文件名，不含存储路径                     |
| `file_type`、`mime_type` | VARCHAR     | 业务文件分类与媒体类型                               |
| `file_size`              | BIGINT      | 字节数；实体 `fileSize` 为数值，对外字段 `sizeBytes` |
| `file_url`               | VARCHAR     | 内部对象存储定位信息，不对外返回                     |
| `status`                 | VARCHAR     | 处理状态，由 `FileStatus` 定义                       |
| `error_message`          | TEXT，可空  | 可向用户展示的处理失败原因                           |

原始文件在 MinIO，数据库只保存信息。文本和图片处理后可用；PDF/DOCX 为仅存储状态。图片描述和文本片段完成入库后，才能标记为可引用。

### `documents_chunks`：用于检索的片段

| 列             | 类型         | 实体表示与用途                                                                          |
| -------------- | ------------ | --------------------------------------------------------------------------------------- |
| `id`           | 自增 BIGINT  | 内部主键，`string`                                                                      |
| `project_id`   | BIGINT 外键  | 查询必须带此过滤条件，限制在当前项目                                                    |
| `knowledge_id` | BIGINT 外键  | 所属文件；删除文件时级联删除片段                                                        |
| `content`      | TEXT         | 模型回答时使用的原文片段或图片描述                                                      |
| `embedding`    | VECTOR(1536) | 当前实体按 pgvector 文本格式读写，为 `string`；模型接口通常产出数值数组，需在实现时转换 |
| `metadata`     | JSONB，可空  | 原文位置、片段序号等附加信息；具体业务结构待定义                                        |
| `created_at`   | TIMESTAMPTZ  | 创建时间                                                                                |

HNSW 索引用于加速向量相似度查询，不代替项目过滤。实际模型必须匹配当前维度；若变更，灌入数据前统一迁移，不混用不同维度或不兼容模型。片段来源与公开标识问题见 Q-05/Q-06。

## 5. 生成任务与条件状态

### `runs`：一次生成任务

| 列                            | 类型                 | 含义                                                                   |
| ----------------------------- | -------------------- | ---------------------------------------------------------------------- |
| `conversation_id`             | BIGINT 外键          | 所属会话                                                               |
| `user_message_id`             | BIGINT 外键          | 初始触发消息                                                           |
| `assistant_message_id`        | BIGINT 外键          | 助手占位消息；暂停恢复后继续使用                                       |
| `status`                      | VARCHAR              | 排队、运行、等待输入或终态；具体值见 `RunStatus`                       |
| `finish_reason`               | VARCHAR，可空        | 终态结束原因，见 `FinishReason`                                        |
| `usage`                       | JSONB，可空          | 模型用量；业务结构与共享 `Usage` 对齐                                  |
| `metadata`                    | JSONB，可空          | 持久保存当前 `Interrupt` 和工具执行摘要；不在 `Run` 查询响应中直接返回 |
| `error_code`、`error_message` | VARCHAR / TEXT，可空 | 失败信息，映射为对外 `error`                                           |
| `finished_at`                 | TIMESTAMPTZ，可空    | 终态时间                                                               |

暂停记录是恢复任务的必要依据，不能只放内存，也不能把此列简单称为“非权威扩展信息”。当前只有列和通用暂停定义，具体恢复逻辑尚待实现。

同一会话只允许一个活跃任务是目标业务规则；现有迁移没有对应的唯一约束，需在 P0-06 明确并发保护，不能只检查后再分别插入。

### `agent_states`：会话当前条件与步骤

| 列                 | 类型              | 含义                                                            |
| ------------------ | ----------------- | --------------------------------------------------------------- |
| `id`               | 自增 BIGINT       | 内部主键，`string`                                              |
| `conversation_id`  | BIGINT 外键，唯一 | 每个会话一行最新状态                                            |
| `current_step`     | VARCHAR           | Agent 当前执行步骤；具体业务定义尚待实现，不同于 SSE 的显示阶段 |
| `version`          | INT，默认 0       | 更新状态时的版本检查依据                                        |
| `constraints_data` | JSONB，可空       | 已确认条件；业务字段、来源信息的共享定义尚待补齐                |
| `updated_at`       | TIMESTAMPTZ       | 状态更新时间                                                    |

状态字段存在不代表已经具备恢复能力；还需要事务、版本比较和明确的执行检查点。

## 6. 已有索引与关联

| 表                 | 现有索引或约束                                        | 用途                   |
| ------------------ | ----------------------------------------------------- | ---------------------- |
| 7 张对外资源表     | `uuid` 唯一                                           | 根据外部标识查资源     |
| `users`            | `email` 唯一                                          | 账号去重和登录查询     |
| `projects`         | `user_id`                                             | 查询某用户项目         |
| `conversations`    | `(project_id, updated_at DESC)`                       | 项目会话与最近活跃会话 |
| `messages`         | `(conversation_id, created_at DESC)`、GIN(`metadata`) | 消息分页与附加数据查询 |
| `runs`             | `(conversation_id, created_at DESC)`                  | 查询会话任务           |
| `knowledge_base`   | `project_id`                                          | 项目文件列表           |
| `documents_chunks` | `knowledge_id`、HNSW(`embedding vector_cosine_ops`)   | 文件片段和向量检索     |
| `assets`           | `(project_id, updated_at DESC)`                       | 命名方案列表           |
| `agent_states`     | `conversation_id` 唯一                                | 每会话一个当前状态     |

现有外键使用 `ON DELETE CASCADE`：删除用户影响项目，删除项目影响文件/片段/资产/会话，删除会话影响消息/任务/状态，删除文件影响片段。迁移没有软删除列或回收站，数据库级联也不会清理 MinIO 对象，删除接口实现还需处理 [Q-08](./待确认问题.md#q-08-删除行为与对象存储清理)。

## 7. 设计理由

结构化条件单独保存，避免每次从完整聊天记录重新推测。草稿覆盖保存，关键图随消息保留，避免每次鼠标移动都写入一份历史大对象。复制会话采用独立数据，避免删除或修改源会话影响新讨论。卡片随消息保存，便于一起获取与渲染，但状态更新仍需保持事务一致。

这些理由约束后续实现，不代表当前 CRUD、模型生成或历史恢复已经完成。接口映射见 [API 数据模型](./API文档/10.%20数据模型.md)。
