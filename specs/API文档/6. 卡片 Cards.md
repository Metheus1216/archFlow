# 6\. 卡片 Cards

### 6\.1 卡片数据结构



```JSON
{
  "id": "card_1",
  "messageId": "msg_12",
  "kind": "single",
  "title": "数据库选型",
  "options": [
    { "value": "pg",    "label": "PostgreSQL", "description": "关系型，事务强" },
    { "value": "mongo", "label": "MongoDB",    "description": "文档型，灵活" }
  ],
  "status": "pending",
  "answer": null,
  "createdAt": "2026-11-08T16:40:00+08:00",
  "answeredAt": null
}
```



|字段|说明|
|---|---|
|`id`|卡片 id|
|`messageId`|**所属消息 id**（原设计缺失，导致 4\.2 路径拼不出来）|
|`kind`|`single` 单选 / `multi` 多选 / `text` 自由输入|
|`options`|`text` 类型时为 `[]`|
|`status`|`pending` 待回答 / `answered` 已回答 / `ignored` 用户跳过（忽略） / `expired` 已失效|
|`answer`|**统一为对象**：`{ "values": ["pg"], "isCustom": false }`。单选是长度 1 的数组，多选是多个，`text` 类型也是数组（长度 1）|



> **为什么 ****`answer`**** 用数组**：原设计 `answer: string` 无法表达多选。用数组后单选/多选/自由输入三种形态一套结构，前端组件也只需一套。

### 6\.2 提交卡片回答



```HTTP
POST /api/v1/conversations/:conversationId/messages/:messageId/answer
Idempotency-Key: <uuid>
```



**描述**：用户点选或输入后触发。服务端更新卡片状态，并**继续 Agent 推理**，返回一个新的 run。



**请求体**：



```JSON
{
  "cardId": "card_1",
  "values": ["pg"],
  "isCustom": false
}
```



|字段|必填|说明|
|---|---|---|
|`cardId`|否|v1 一条消息最多一张卡片，可省略；传了就校验是否匹配|
|`values`|是|元素个数与去空白见 `AnswerCardInput`；`multi` 可多个|
|`isCustom`|否|默认 `false`。`true` 表示 `values` 是用户自由输入|



**响应 ****`202 Accepted`**：结构与 5\.1 相同。



```JSON
{
  "runId": "run_9f20",
  "userMessageId": "msg_13",
  "assistantMessageId": "msg_14",
  "streamUrl": "/api/v1/runs/run_9f20/stream",
  "status": "queued"
}
```



**错误**：



|HTTP|code|说明|
|---|---|---|
|409|`CARD_EXPIRED`|卡片已过期|
|422|`VALIDATION_FAILED`|`values` 为空或含空白项|
|409|`CONVERSATION_BUSY`|会话忙，`data.activeRunId`|
|404|`CARD_NOT_FOUND`|卡片不存在|



> **重复提交**：同一卡片再次提交返回 `200` 并重放首次的 run 结果（幂等），不再返回 409。

### 6\.3 卡片状态同步（对交付说明 2 的修正）



**原交付说明 2**：「前端解析流时，如果遇到带 `id` 且 `status` 为 `answered` 的 `constraint-card` 事件，就本地找到对应消息更新 UI」。



**问题**：靠流事件驱动本地状态，一旦漏帧（断线、切后台）就与真服务端不一致。



**本版改为服务端权威**：



1. 卡片**持久化**在 `message.metadata.card`；

2. 提交回答后，服务端**立即**把 `status` 改为 `answered` 并写入 `answer`；

3. 前端在收到 `202` 响应后**乐观更新本地卡片**（置灰不可点），等流结束后**重新拉消息列表**做最终校准；

4. 刷新页面后，`GET /messages` 里 `card.status === "pending"` 的卡片仍然可答 —— **不会丢**。
