# 6. 条件卡片

> 目标：用户通过卡片补充条件，服务端保存回答后继续任务。当前卡片数据定义已存在，实际回答和暂停恢复尚未实现。

## 6.1 卡片结构

卡片使用共享 `ConstraintCard`，随 `message.metadata.card` 保存。一条消息第一版最多一张卡片。

```json
{
  "id": "card_1",
  "messageId": "msg_2",
  "kind": "single",
  "title": "预计由几个人开发？",
  "options": [{ "value": "small", "label": "1～3 人" }],
  "status": "pending",
  "answer": null,
  "createdAt": "2026-11-13T16:00:00+08:00",
  "answeredAt": null
}
```

`messageId` 用于找到所属消息。卡片可表示单选、多选或自由输入；自由输入不需要选项。回答统一使用 `CardAnswer` 的 `values` 数组及 `isCustom`，不能为不同卡片分别维护互不兼容的格式。

## 6.2 提交回答

```http
POST /api/v1/conversations/:conversationId/messages/:messageId/answer
Idempotency-Key: <本次操作标识>
```

请求使用 `AnswerCardInput`：

```json
{ "cardId": "card_1", "values": ["small"], "isCustom": false }
```

`cardId` 当前可省略，传入时应匹配消息中的卡片。服务端还要根据卡片类型校验选择数量、允许选项和自定义输入，不能仅凭非空数组就接受任意答案。

卡片对应等待输入中的任务时，继续**原任务**并返回 `202` 与 `RunAccepted`，使用原 `runId` 和 `assistantMessageId`；只有不存在等待中的关联任务且规则允许时才新建任务。恢复响应中的 `userMessageId` 以及暂停点识别仍需补齐，见 [Q-02](../待确认问题.md#q-02-暂停和继续执行的数据还不完整)。

| 情况                       | 响应                                  |
| -------------------------- | ------------------------------------- |
| 成功处理或继续任务         | `202`，返回任务受理结果               |
| 同一卡片已经回答           | `200`，重放首次结果，不重复执行       |
| 卡片已失效                 | `409 CARD_EXPIRED`                    |
| 选择或输入不合法           | `422 VALIDATION_FAILED`               |
| 另有不能接续的任务正在执行 | `409 CONVERSATION_BUSY`，`data: null` |
| 卡片不存在或无权访问       | `404 CARD_NOT_FOUND`                  |

网络重试复用原操作标识。已回答卡片再次提交即使换了标识，也不能触发第二次执行；不同答案不得静默覆盖首次回答。

## 6.3 显示与数据同步

服务端在继续执行前保存卡片状态、回答和条件更新。前端收到成功响应后将卡片显示为已回答；失败时恢复操作并提示原因。`card-updated` 可同步界面，但最终以重新获取的消息为准。

刷新后根据数据库中的卡片恢复界面，仍待回答且未过期的卡片可以继续作答。普通文字回答也要与原卡片及暂停状态协调，不能只更新一份条件 JSON 而留下永久待答卡片。

“跳过”和“改为直接输入”的关联规则仍需在暂停实现中明确；通用审批与结果复核不属于第一版卡片验收。
