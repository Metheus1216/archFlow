# 实现前需要补齐的设计

> 核查日期：2026-11-13。
> 本文记录现有规则、代码与目标之间尚未解决的差异。这里的建议不是新增接口契约；涉及字段的决定必须先落实到 `packages/shared/src/schemas/`，涉及表结构的决定必须补迁移。

## Q-01 拖拽位置如何保存

**冲突**：MVP 要求拖拽后刷新仍保留布局，但 `GraphNode` 不包含坐标，并且是拒绝额外字段的严格对象。仅保存现有 `Graph` 无法完成这一要求。

**建议**：继续让 `Graph` 表达节点和连接关系，另定义按节点 ID 对应的位置和画布视图数据。先确定它在草稿、资产、历史快照中的保存与恢复方式，再修改对应 Zod、接口和数据库说明。不要直接向 `GraphNode` 塞入未声明字段，也不要把“重新自动排版”算作“恢复用户布局”。

**影响**：P0-16、P0-18，MVP 的 AC4/AC6。

## Q-02 暂停和继续执行的数据还不完整

**已有**：`Interrupt` 有 ID、类型、步骤、过期时间和一个通用 `payload` 对象；SSE 支持 `interrupt` 和 `run-start.resume`。

**缺口**：澄清、审批、复核各自的 `payload` 尚无具体 Zod 定义；普通消息和卡片作答请求没有显式的暂停 ID/版本。需要确定服务端如何识别用户回答的是哪个暂停点、如何拒绝过期回答，以及继续执行时响应中的 `userMessageId` 指向初始消息还是本次输入。

**建议**：P0-07 先实现澄清卡片，并明确暂停记录、卡片和恢复请求的关联。保留同一 `runId` 与 `assistantMessageId` 的既定行为；审批与复核留到 P1，不能仅凭一个通用对象宣称全部交互已定稿。

**影响**：P0-01 的字段细化、P0-06、P0-07、P1-01。

## Q-03 进程退出后的未完成任务怎样处理

**已有要求**：浏览器断线时任务继续，缓存失效时从数据库恢复显示。

**缺口**：第一版任务运行在 API 进程内，没有队列或独立执行进程。进程退出会停止实际计算，即使数据库里还保留 `running`。仅重放消息不能让计算自动继续，也不能直接发送成功结束事件。

**待定策略**：服务重启后，把无法继续的任务标记为失败，保留部分结果并允许重新发起；或者补充足够的执行检查点，真正继续原任务。两者要选定并覆盖测试。`waiting_input` 因为本来就在等待，可以根据已保存的暂停记录恢复，但仍依赖 Q-02 的具体定义。

**影响**：P0-03、P0-06、断线恢复验收。

## Q-04 统一错误规则与当前过滤器有差异

**目标规则**：错误响应 `data` 始终为 `null`；普通字段校验失败按 API 文档返回 `422 VALIDATION_FAILED`，图过大与图结构错误分别使用对应错误码。

**当前实现**：全局过滤器对普通 Zod 校验错误返回 400；成功响应没有统一序列化/校验机制；未指定 Zod 的参数会被校验管道原样放行。异常路径已有 traceId，不代表成功、204 和流式路径已经覆盖。

**待补**：P0-02 统一校验状态码、为各 Controller 明确绑定请求 Schema，并在成功出口序列化与校验数据。原文档要求从错误 `data` 读取 `activeRunId`、`currentVersion` 已纠正：冲突后重新获取会话；任务恢复使用客户端已知的任务 ID。若产品要求新设备自动发现活跃任务，需另补正常查询契约。

**影响**：P0-02、P0-06、P0-14～P0-16。

## Q-05 内部表的 UUID 与项目规则不一致

**当前实现**：7 张可对外访问的资源表有内部 `id` 和外部 `uuid`；`documents_chunks`、`agent_states` 两张内部表没有 `uuid`。

**冲突**：项目规则要求所有表都有 `uuid`。本次文档只如实记录差异，没有自行修改规则或数据库。

**待补**：按现行规则为内部表补迁移，或明确批准内部表例外。引用资料当前只返回文件 ID 和片段，若需要稳定定位到具体切片，也要同时设计公开标识和对应 Zod。

**影响**：P0-01 的数据库一致性、P0-08、P0-17。

## Q-06 模型配置和向量维度需要真实验证

**已有方向**：主对话使用 DeepSeek chat 类模型，图片理解与向量化使用千问；SDK 直接调用，不引入重型编排框架。

**待补**：确认实际模型名、各任务的环境变量、工具调用/结构化输出支持情况，以及向量模型能否输出当前数据库要求的维度。`.env.example` 中的通用 `OPENAI_*` 目前只是占位，API 的环境校验还没有接这些字段。

在写入任何文档向量前完成维度验证。若需要修改维度，统一修改表结构和索引；查询和入库必须使用兼容的模型，不能混用旧数据。

**影响**：P0-09、P0-17、P0-08。

## Q-07 分页与复制历史的边界尚需落实

会话列表的路径已经规划，但尚无专用列表查询/响应定义；应复用公共分页规则和会话元信息，在实现前确认导出。复制会话还要确定最大复制范围、源消息没有图时如何选取草稿、消息和卡片的新 ID 如何重建，以及 Agent 条件状态如何初始化。

这些决定要保证新会话独立，并避免复制一个仍可继续执行的旧任务。当前“物理复制”方向已定，不能在实现时无说明地换成依赖原会话的指针关系。

**影响**：P0-15、P0-18。

## Q-08 删除行为与对象存储清理

当前迁移使用数据库级联删除，没有软删除列，也没有回收站和恢复接口。当前规格据此不承诺“30 天内可恢复”；若要提供恢复功能，必须另行设计并修改数据结构。

数据库级联不会删除 MinIO 文件。实现删除时需要确定文件对象的清理、部分失败后的重试，以及正在执行的任务如何停止。图片类型识别、文件数量限制和解析超时也应在上传任务中确定，不能仅根据扩展名就把文件送入处理流程。

**影响**：P0-12、P0-15、P0-17、P0-18。
