# 5. 生成任务与流式回复（Agent）

> 当前只具备共享数据定义，任务受理、模型执行和服务端事件流尚未实现。本文描述目标协议。

## 5.0 请求分工

发消息 POST 只负责校验和保存任务，返回稳定的任务 ID；独立 GET 获取持续事件。这样重连不会重新发起推理，也可以单独查询或取消。

| 请求                                                  | 职责                         |
| ----------------------------------------------------- | ---------------------------- |
| `POST /api/v1/conversations/:conversationId/messages` | 保存消息并受理任务           |
| `GET /api/v1/runs/:runId/stream`                      | 持续接收或补发事件           |
| `GET /api/v1/runs/:runId`                             | 查询状态，连接异常时定期查询 |
| `POST /api/v1/runs/:runId/cancel`                     | 请求取消并保存已有结果       |

浏览器统一使用 `@microsoft/fetch-event-source`，携带认证请求头；不使用原生 `EventSource`，不把凭证放进 URL。设计理由见[架构规划](../架构规划.md)。

## 5.1 发送消息

```http
POST /api/v1/conversations/:conversationId/messages
Idempotency-Key: <本次操作标识>
```

请求使用 `SendMessageInput`：

```json
{ "content": "设计一个学校社团活动报名系统" }
```

`attachments` 已预留为文件 ID 列表，但第一版不提供聊天附件入口。项目文件通过知识库上传；未来启用该字段前，仍需检查文件属于同一项目且可引用。

服务端读取已保存的会话草稿，不接收 `currentGraph`。前端有未保存编辑时先保存，保存失败或版本冲突时不继续发起生成。

首次受理返回 `202`，`data` 使用 `RunAccepted`：

```json
{
  "runId": "run_1",
  "userMessageId": "msg_1",
  "assistantMessageId": "msg_2",
  "streamUrl": "/api/v1/runs/run_1/stream",
  "status": "queued"
}
```

`queued` 代表已保存、待开始，不代表存在消息队列。`streamUrl` 由服务端生成，客户端使用返回路径并按配置解析 API 来源；不再自行拼接业务前缀。

同一会话有运行中任务时返回 `409 CONVERSATION_BUSY`，`data: null`。等待输入的任务可继续同一任务；具体恢复绑定和消息 ID 语义仍需按 [Q-02](../待确认问题.md#q-02-暂停和继续执行的数据还不完整)补齐。会话不存在/越权返回 404；消息不合规则按全局校验规则处理。

## 5.2 事件流

```http
GET /api/v1/runs/:runId/stream
Authorization: Bearer <accessToken>
Last-Event-ID: 12
```

`Last-Event-ID` 仅在已收到事件时发送。服务端成功响应设置：

```http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

关闭代理缓冲，避免事件等到结束才交给浏览器。业务帧格式如下，帧间有空行：

```text
id: 12
data: {"type":"text-delta","messageId":"msg_2","content":"建议"}

```

同一任务内业务帧 ID 递增；注释心跳不参与业务去重。没有输出时约每 15 秒发送注释心跳，避免空闲超时。

### 事件含义

数据以 `SseFrame` 为准。首次连接或全量恢复包含 `run-start`；按已有帧 ID 增量续传时可以从下一业务帧开始，客户端已有任务/消息关联，不要求补发旧首帧。

| `type`            | 处理方式                                          |
| ----------------- | ------------------------------------------------- |
| `run-start`       | 关联任务与助手消息；`resume: true` 时保留已有文字 |
| `status`          | 显示分析、检索、生成图、收尾阶段                  |
| `text-delta`      | 默认追加；`replace: true` 时覆盖该消息文字        |
| `graph`           | 使用已校验的业务图整体替换当前生成结果            |
| `citation`        | 显示项目文件来源                                  |
| `constraint-card` | 根据消息 ID 显示问题卡片                          |
| `card-updated`    | 同步回答后的卡片状态                              |
| `interrupt`       | 保存等待输入状态，关闭连接，不作为任务结束        |
| `title`           | 更新会话标题                                      |
| `usage`           | 记录调用量和耗时，不用于用户计费                  |
| `error`           | 显示生成失败，随后用终态事件结束                  |
| `done`            | 记录结束原因，读取最终消息                        |

正常终态还要发送 `[DONE]` 作为传输结束标记。客户端可在 `done` 开始收尾，但须识别 `[DONE]`/正常关闭，不能因此重复刷新或自动重连。等待输入只发 `interrupt`，不发 `done` 或 `[DONE]`。

### 重连与数据库恢复

| 情况                            | 处理                                                     |
| ------------------------------- | -------------------------------------------------------- |
| 有有效帧位置，缓存仍在          | 仅补发下一帧及之后的内容，再接实时事件                   |
| 没有帧位置，缓存仍在            | 从头补发；前端按消息 ID 重建，避免重复文字               |
| 等待输入                        | 先补足文字/卡片，再发送保存的暂停事件后关闭              |
| 缓存失效                        | 从数据库恢复全量消息与对应图，再按实际任务状态继续或结束 |
| 已知位置大于仍有效缓存的最新 ID | `409 RUN_NOT_RESUMABLE`，刷新数据并查询任务              |
| 任务或关联消息缺失              | 任务不存在/越权为 404；任务存在但关联损坏为 409          |

缓存失效时不能先用过时帧序号拒绝重连，应先进入数据库恢复。全量文本使用 `replace: true`；图使用该任务助手消息的 `graph_snapshot`，缺失则不发送，不拿后来会话的新草稿冒充历史结果。

仍在运行的任务恢复后继续实时事件，不发送终态。等待输入则恢复暂停；只有已确认成功、失败或取消的任务才发送对应 `done`。全量恢复、增量切换与帧序号衔接需要 P0-06/P1-08 测试覆盖。

生成期间分批写入 `messages.content`，初始节流策略约每秒或每 200 token，先到者触发；结束时最终写入文字、图、引用、用量和任务终态。事件缓存只用于补发，任务结束后保留 10 分钟。

断开浏览器连接不会取消任务。进程退出会停止计算，不能仅靠数据库内容自动续算；重启处理仍需 [Q-03](../待确认问题.md#q-03-进程退出后的未完成任务怎样处理)确定。

### 等待用户回答

暂停前保存 `Interrupt` 和卡片，把任务改为 `waiting_input`；回答后继续同一 `runId` 与 `assistantMessageId`，`run-start` 携带 `resume: true`。已完成的工具写入不重复执行。

默认等待期限 24 小时，可配置。超时或主动取消进入取消状态。第一版只实现澄清卡片；通用审批和复核留到后续。`payload` 的具体结构和恢复请求绑定尚未定稿，不能仅凭现有通用对象实现所有交互。

## 5.3 查询任务状态

```http
GET /api/v1/runs/:runId
```

返回 `200`，`data` 使用 `Run`：

```json
{
  "id": "run_1",
  "conversationId": "cnv_1",
  "userMessageId": "msg_1",
  "assistantMessageId": "msg_2",
  "status": "succeeded",
  "finishReason": "stop",
  "createdAt": "2026-11-13T16:00:00+08:00",
  "finishedAt": "2026-11-13T16:00:09+08:00",
  "error": null
}
```

连接连续失败可定期查询该接口。收到终态后拉取消息；收到等待输入则恢复暂停界面并停止普通轮询，不能一直等到终态。

## 5.4 取消任务

```http
POST /api/v1/runs/:runId/cancel
```

返回 `202` 和 `CancelResult`，表示已经接受取消请求，可能仍返回当前 `running`。服务端尽快停止模型调用，保存已有结果，写入 `canceled` 终态；最终状态通过事件流或查询获得。重复取消和已结束任务的行为在实现中保持幂等并补测试。
